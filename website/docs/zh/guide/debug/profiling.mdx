# 性能分析

通过 `--trace`、`DEBUG=rstest`、Rsdoctor、`samply` 和 Node.js 内置 profiler 定位测试耗时与内存瓶颈。

## 使用 Agent Skills

使用 Coding Agent 排查性能回归时，可以安装 [rstest-debugging](https://github.com/rstackjs/agent-skills#rstest-debugging) skill，引导 Agent 在修改配置或测试代码前先区分瓶颈位于构建启动还是测试执行阶段：

```bash
npx skills add rstackjs/agent-skills --skill rstest-debugging
```

## 常见性能瓶颈

先使用 [`--trace`](#using-trace) 运行一次测试以区分构建耗时与测试执行耗时，再按对应分支排查：

1. **构建耗时占主导**（常见于 `jsdom` 或 `happy-dom` 等类浏览器环境，默认会打包 `node_modules` 依赖而非像 `node` 环境那样 externalize）：
   - 运行 `DEBUG=rstest rstest run`，检查构建日志和 `dist/.rstest-temp`（或 [`output.distPath.root`](/config/build/output#outputdistpath)）下的临时产物体积。
   - 设置 [`output.bundleDependencies: false`](/config/build/output#outputbundledependencies) 将第三方依赖 externalize（不适用于[浏览器模式](/guide/browser-testing)），或通过 [`output.externals`](/config/build/output#outputexternals) 排除特定大体积包。
   - 对重复执行的 `rstest run` 开启 [`performance.buildCache`](/config/build/performance#performancebuildcache)，或使用 [Rsdoctor](#使用-rsdoctor) 分析 loader 与插件的编译耗时。
2. **测试执行耗时占主导**（启动快，但单个文件或用例慢）：
   - 通过 `--reporters=verbose`（[`verbose` 报告器](/guide/basic/reporters#详细报告器)）或 `--trace` 摘要查看各文件与用例的耗时排序。
   - 使用 [samply](#使用-samply) 或 [Node.js profiling](#nodejs-profiling) 采样热点代码（见 [Profiler](#profiler)）。

## 使用 --trace \{#using-trace}

`--trace` 会把一次运行按 phase、suite、case 拆分成 slices。当 reporter 末尾的 `Duration` 单值不足以判断时间分布时，可以使用它定位瓶颈。

```bash
npx rstest run --trace
```

`--trace` 是可选开关。开启后每次运行会记录带 status 和 retry count 标注的 suite 与 case slices，在每个 phase 边界采样一次 heap 计数，并为每个测试文件的各个 phase 生成一个 slice：

- `prepare`：初始化 worker 运行时、全局 API，以及启用覆盖率时的 coverage provider。
- `envSetup`：初始化 test environment。`node` 环境下，以及非 isolate 的 worker 已锁定该环境时，耗时接近 0。
- `load`：接收该测试入口的构建产物。host 侧生成产物的耗时会记录为 host span。
- `setupFiles`：执行配置的 setup 文件。
- `collect`：执行测试模块并构建 suite 与 case 树，包含延迟执行和异步的 `describe` 回调。
- `tests`：运行用例及其 hooks。
- `coverage`：从 provider 收集覆盖率数据。未启用覆盖率，或该文件在此之前 bail 或抛错时，不会出现。
- `teardown`：清理 coverage provider 和 worker 状态；启用 `isolate` 时还会清理 test environment。

Node pool 还会记录 `file:load` 汇总区间，覆盖 worker 内的产物加载、setup 文件执行、测试模块求值与 suite 收集（对应 `TestFileResult.loadDuration`）。

浏览器模式只记录 `prepare` 和 `tests` 两个 phase，由 host 根据页面发来的消息计时。

Rstest 会向 `<rootPath>/.rstest/` 写入两个文件，并在 watch 模式每次重新运行时替换它们：

- `trace-<timestamp>.summary.md`：对最慢的 phase、文件和测试用例排序的 markdown 摘要，相同内容会同时打印到终端。
- `trace-<timestamp>.json`：Perfetto-compatible 的 trace，用于可视化 UI。

建议先看摘要。当你还需要观察多个 worker 之间的工作如何重叠时，再打开 trace。

![Perfetto UI 中显示在 rstest 仓库执行 npx rstest --trace 产出的 trace](https://assets.rspack.rs/rstest/assets/rstest-trace-perfetto.png)

在 TTY 下，Rstest 会启动一个本地 helper server，使打印出的链接直接在 Perfetto UI 中打开 trace。在 CI 下不会启动该 server，此时可以将 trace 文件作为 artifact 上传，再拖入 [ui.perfetto.dev](https://ui.perfetto.dev) 查看。

:::tip
借助 Coding Agent 排查性能问题时，把两个文件都交给它：摘要给出排序结果，trace 包含完整事件数据。可配合 [rstest-debugging](#使用-agent-skills) 技能使用。
:::

## 实验性内存诊断 \{#experimental-memory-diagnostics}

通过 `DEBUG=rstest:memory` 排查编译、测试执行和覆盖率报告阶段的内存增长。这是一项实验调试能力，命名空间和输出格式可能会调整。

```bash
DEBUG=rstest:memory npx rstest run --coverage
```

开始采集时，Rstest 会打印 `.rstest/trace-rss-<timestamp>-<pid>.jsonl` 的路径。请在 CI 中保存这个文件，包括运行失败的任务。每条 JSON 记录都会立即写出，因此 Rstest 进程被强杀后，已经写出的记录仍然可读。

日志包含：

- 每秒以及主进程操作边界的 RSS、V8 堆使用量和容量、external 内存、ArrayBuffer 内存，单位均为字节。
- 各通过 Node.js worker 执行的 project（包括 `node`、`jsdom`、`happy-dom` 和自定义测试环境）的编译开始和结束、附带 project 和测试文件信息的主进程操作，以及覆盖率收集和报告生成阶段。最终各 executor 的覆盖率合并、已收集覆盖率的复制都有独立的操作边界记录。
- worker 启动后、每秒、每个测试文件前后及 worker fixture 清理前后的内存。worker 记录带有 `role: "worker"`、`workerId`、`pool`、PID、`threadId` 和采样时的 `sampledAt` 时间戳；执行任务时还包含 project 和测试文件路径。`worker:exit` 标记这个 worker 生命周期的结束。
- `project:assets` 记录各 project 的产物数量和字节数。`jsBytes`、`sourceMapBytes`、`otherBytes`、`totalBytes` 分别表示 JS、独立 source map、其他产物和合计大小。`unavailableAssetCount` 表示未能获取大小的文件数，合计只包含成功统计的文件。内联 source map 计入 `jsBytes`。
- Linux 上可读取 cgroup v2 文件时，于启动、周期采样、运行报错和停止时记录当前内存用量、限制、可用的峰值数据，以及累计的 `oom` / `oom_kill` 计数，不在每个操作边界读取这些文件。`cgroupPath` 标识采样的 cgroup。

主进程记录带有 `role: "host"`。forks 和 vmForks 的 `rssScope: "worker-process"` 表示独立进程；threads 和 vmThreads 的 `rssScope: "shared-process"` 表示这个 PID 下所有线程共享的进程 RSS，汇总时只计一次。heap 数据属于各自的 V8 isolate，可以分开查看。workerId 会复用，需要结合 PID 和 threadId 区分生命周期。采样异步送达，主线程被阻塞时可能延迟；RSS 相加可能重复计算共享页。浏览器进程、prebundle 进程及测试自行启动的子进程拥有额外内存。cgroup 数据覆盖该组及其子组，可能包含其他进程和此前运行的数据。主线程被阻塞时，定时采样也会暂停；操作开始时写出的记录仍能帮助定位被强杀时正在执行的同步操作。

`DEBUG=rstest:memory` 可以独立使用，也可以与 `--trace` 一起采集耗时信息。

它要求逗号分隔的 `DEBUG` 值中包含完整命名空间，`DEBUG=rstest` 和 `DEBUG=*` 不会启用它。单独开启时，不会启用 verbose 日志或将构建产物写入磁盘。通过 JavaScript API 运行时，该环境变量同样会开启采集，但不会打印文件路径。watch 模式下会一直采集到会话关闭。

采样、文件写入和关闭的异常会被隔离，不会因诊断错误导致测试失败。内存日志会增加采样和同步文件写入开销。缺少最后的 `stop` 记录表示采集未正常关闭，需要结合退出状态、系统日志和 cgroup OOM 计数变化判断原因。

## 使用 Rsdoctor

[Rsdoctor](https://rsdoctor.rs/) 是一款为 Rspack 生态量身打造的构建分析工具。

当你需要调试 Rstest 的构建产物或构建过程时，可以借助 Rsdoctor 来提升排查问题的效率。

### 快速上手

在 Rstest 中，你可以通过 [@rsdoctor/core](https://www.npmjs.com/package/@rsdoctor/core) 开启 Rsdoctor 分析：

1. 安装 Rsdoctor：

import { PackageManagerTabs } from '@theme';

<PackageManagerTabs command="add @rsdoctor/core -D" />

2. 在 CLI 命令前添加 `RSDOCTOR=true` 环境变量：

```json title="package.json"
{
  "scripts": {
    "test:rsdoctor": "RSDOCTOR=true rstest run"
  }
}
```

由于 Windows 不支持上述用法，你也可以使用 [cross-env](https://npmjs.com/package/cross-env) 来设置环境变量，这可以确保在不同的操作系统中都能正常使用：

```json title="package.json"
{
  "scripts": {
    "test:rsdoctor": "cross-env RSDOCTOR=true rstest run"
  },
  "devDependencies": {
    "cross-env": "^7.0.0"
  }
}
```

在项目内执行上述命令后，Rstest 会自动注册 Rsdoctor 的插件，并在构建完成后打开本次构建的分析页面，请参考 [Rsdoctor 文档](https://rsdoctor.rs/) 来了解完整功能。

![rsdoctor-rstest-outputs](https://assets.rspack.rs/rstest/assets/rsdoctor-rstest-outputs.png)

## Profiler

可以先确认 [`--trace`](#using-trace) 是否已经能定位问题，它不需要额外工具。需要更底层的采样数据时，按分析目标选择：

- **CPU 耗时分布**：使用 [samply](#使用-samply)（可同时分析 Rstest 主进程与 `forks` / `vmForks` worker 进程）或 `--cpu-prof`。
- **内存分配**：使用 [Node.js profiling](#nodejs-profiling) 中的 `--heap-prof`（`samply` 不采集内存数据）。
- **断点 / 单步调试**：见[调试测试 worker](/guide/debug/debugging#调试测试-worker)。

## 使用 samply

:::note
在 macOS 上对 Node.js 代码进行 profiling 需要 Node.js 22.16+。
:::

[samply](https://github.com/mstange/samply) 支持同时对 Rstest 主进程和测试 worker 进行性能分析：

```bash
samply record -- node --perf-prof --perf-basic-prof --interpreted-frames-native-stack ./node_modules/@rstest/core/bin/rstest.js run
```

Rstest 会将主进程上的 `--perf-prof`、`--perf-basic-prof` 和 `--interpreted-frames-native-stack` 透传给 `forks` 和 `vmForks` worker。对于 `threads` 和 `vmThreads`，worker 与主进程共享同一个 Node.js 进程，主进程上的这些 V8 参数已经覆盖整个进程（**不要**通过 `--pool.execArgv` 传入它们，Node.js `worker_threads` 会抛出 `ERR_WORKER_INVALID_EXEC_ARGV`）。

执行结束后，`samply` 会自动在 [Firefox Profiler](https://profiler.firefox.com/) 中打开采样结果，选择 Node.js 线程即可查看 JavaScript 侧的耗时分布。

![rstest-samply-profiling](https://assets.rspack.rs/rstest/assets/rstest-samply-profiling.png)

## Node.js profiling

Rstest 会将主进程上的 `--cpu-prof*`、`--heap-prof*` 和 `--diagnostic-dir` 透传给所有 pool（`forks`、`vmForks`、`threads` 和 `vmThreads`）的 worker。

采集 CPU profile：

```bash
node --cpu-prof --cpu-prof-dir=./cpu-prof ./node_modules/@rstest/core/bin/rstest.js run
```

采集堆内存 profile：

```bash
node --heap-prof --heap-prof-dir=./heap-prof ./node_modules/@rstest/core/bin/rstest.js run
```

生成的 `.cpuprofile` 或 `.heapprofile` 文件可使用 [Visual Studio Code](https://code.visualstudio.com/docs/nodejs/profiling#_analyzing-a-profile) 或 [Chrome DevTools](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots) 打开分析。

:::tip
主进程上的 `--inspect*` 参数会被 worker 过滤，仅作用于 Rstest 主进程。如需单步调试测试 worker 代码，请使用 `--pool.execArgv=--inspect-brk`，详见[调试测试 worker](/guide/debug/debugging#调试测试-worker)。
:::
