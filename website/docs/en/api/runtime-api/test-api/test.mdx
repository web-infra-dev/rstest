# Test

`test` (alias: `it`) defines a test case and supports per-test options, parameterized runs, chainable modifiers, and custom fixtures via `test.extend`.

## test

- **Type:**

```ts
(name: string | Function, fn?: (testContext: TestContext) => void | Promise<void>, timeout?: number): void;
(name: string | Function, options: TestOptions, fn?: (testContext: TestContext) => void | Promise<void>): void;
```

Defines a test case.

```ts
import { expect, test } from '@rstest/core';

test('adds two numbers', () => {
  expect(1 + 1).toBe(2);
  expect(1 + 2).toBe(3);
});
```

<ApiMeta addedVersion="0.12.3" />

`name` can be a string or a named function. Rstest reads the function's `name` property without calling it (anonymous functions display as `<anonymous>`). This also applies to `test.each` and `test.for`.

### TestOptions

<ApiMeta addedVersion="0.11.1" />

Pass a `TestOptions` object as the **second argument** (before the test callback) to configure a single test:

```ts
test('flaky network call', { retry: 3 }, async () => {
  /* ... */
});
```

Passing a number as the **last argument** is a shorthand for `{ timeout: n }`:

```ts
test('runs within 3s', async () => {
  /* ... */
}, 3000);
```

`TestOptions` fields:

- `timeout?: number` — per-test timeout in milliseconds. Overrides [`test.testTimeout`](/config/test/test-timeout).
- `retry?: number` — re-runs the test up to this many times on failure, stopping on the first pass. Overrides [`test.retry`](/config/test/retry).
- `repeats?: number` — additional runs for this test after the initial run. Overrides [`test.repeats`](/config/test/repeats); see that page for lifecycle and retry interaction.
- `meta?: TaskMeta` — added in `0.11.1`. Initial JSON-serializable metadata for the test result. Inside a `describe` with `meta`, the test inherits a copy of the suite metadata and test-level keys override inherited keys.

`TaskMeta` and `TaskMetaValue` are exported from `@rstest/core`:

```ts
type TaskMeta = Record<string, TaskMetaValue>;

type TaskMetaValue =
  | string
  | number
  | boolean
  | null
  | TaskMetaValue[]
  | { [key: string]: TaskMetaValue };
```

```ts
// 10 total runs; first failure short-circuits the rest
test('stays green across runs', { repeats: 9 }, async () => {
  /* ... */
});

test('records metadata', { meta: { owner: 'team-a' } }, (context) => {
  context.task.meta.startedBy = 'runtime';
});
```

Mutating `context.task.meta` during execution updates the `TestResult.meta` object delivered to reporters and the programmatic API.

`test.each` and `test.for` accept `TestOptions` in the same second-argument position and apply it to every generated case.

## test.only

Runs only the tests marked with `only` in the file.

```ts
test.only('run only this test', () => {
  // ...
});
```

## test.skip

Skips the test at definition time.

```ts
test.skip('skip this test', () => {
  // ...
});
```

To skip dynamically while a test is already running, call `context.skip()`. It aborts the test immediately so later statements do not execute, and reports the test as skipped:

```ts
test('skip at runtime', (context) => {
  context.skip();

  // Not executed
  expect(1 + 1).toBe(3);
});
```

## test.todo

Marks a test as todo without executing it.

```ts
test.todo('should implement this test');
```

## test.each

- **Type:**

```ts
type TestCall<Fn> = {
  (name: string | Function, fn?: Fn, timeout?: number): void;
  (name: string | Function, options: TestOptions, fn?: Fn): void;
};

// Object rows: each row is passed as a single argument
test.each<T extends Record<string, unknown>>(
  cases: readonly T[],
): TestCall<(param: T) => void | Promise<void>>;
// Tuple / array rows: every row is an array, spread into the arguments
test.each<T extends readonly [unknown, ...unknown[]]>(
  cases: readonly T[],
): TestCall<(...args: [...T]) => void | Promise<void>>;
test.each<T extends readonly unknown[]>(
  cases: readonly T[],
): TestCall<(...args: [...T]) => void | Promise<void>>;
// Mixed or scalar rows: each row is passed as a single argument
test.each<T>(
  cases: readonly T[],
): TestCall<(param: T) => void | Promise<void>>;
// Tagged template literal table
test.each<T extends Record<string, unknown>>(
  strings: TemplateStringsArray,
  ...expressions: unknown[]
): TestCall<(param: T) => void | Promise<void>>;
```

Runs the test callback once for each entry in `cases` or in a tagged template table.

Rows are spread into `fn` arguments only when every row is an array. If any row is not an array, every row is passed as a single argument:

```ts
test.each([null, 42, ['a']])('rejects %o', (value) => {
  // The third case receives ['a'], not 'a'.
  expect(isValid(value)).toBe(false);
});
```

You can format test names using [printf placeholders](https://nodejs.org/api/util.html#utilformatformat-args) (`%s`, `%d`, `%i`, `%f`, `%j`, `%o`, `%O`, `%c`, `%#` for 0-based index, `%$` for 1-based index, `%%` for literal `%`) or `$property` placeholders for object rows:

```ts
test.each([
  [1, 2, 3],
  [2, 2, 4],
])('adds %i + %i to equal %i', (a, b, sum) => {
  expect(a + b).toBe(sum);
});

test.each([
  { a: 1, b: 1, sum: 2 },
  { a: 1, b: 2, sum: 3 },
])('adds $a + $b to equal $sum', ({ a, b, sum }) => {
  expect(a + b).toBe(sum);
});
```

With tagged template literals, the first row defines column headers separated by `|` and subsequent rows supply values via `${...}`. Pass an explicit generic type parameter to type the row object:

```ts
test.each<{ a: number; b: number; expected: number }>`
  a    | b    | expected
  ${1} | ${2} | ${3}
  ${2} | ${3} | ${5}
`('$a + $b = $expected', ({ a, b, expected }) => {
  expect(a + b).toBe(expected);
});
```

## test.for

- **Type:**

```ts
type TestCall<Fn> = {
  (name: string | Function, fn?: Fn, timeout?: number): void;
  (name: string | Function, options: TestOptions, fn?: Fn): void;
};

test.for<T>(
  cases: readonly T[],
): TestCall<(param: T, context: TestContext) => void | Promise<void>>;
test.for<T extends Record<string, unknown>>(
  strings: TemplateStringsArray,
  ...expressions: unknown[]
): TestCall<(param: T, context: TestContext) => void | Promise<void>>;
```

Alternative to `test.each` that always passes each row as a single `param` argument (without spreading arrays) and passes [`TestContext`](#testcontext) (plus any extended fixtures) as the second argument.

```ts
test.for([
  { a: 1, b: 2 },
  { a: 2, b: 2 },
])('adds $a + $b', ({ a, b }, { expect }) => {
  expect(a + b).matchSnapshot();
});
```

Also supports tagged template literals with an optional explicit generic parameter:

```ts
test.for<{ a: number; b: number; expected: number }>`
  a    | b    | expected
  ${1} | ${2} | ${3}
  ${2} | ${3} | ${5}
`('$a + $b = $expected', ({ a, b, expected }, { expect }) => {
  expect(a + b).toBe(expected);
});
```

## test.fails

Marks the test as expected to fail. The test passes if it throws or fails an assertion, and fails if it completes without error.

```ts
test.fails('should fail', () => {
  throw new Error('This test is expected to fail');
});
```

## test.concurrent

Runs consecutive tests marked `concurrent` in the same suite in parallel.

```ts
describe('suite', () => {
  test('serial test', async () => {
    /* ... */
  });
  test.concurrent('concurrent test 1', async () => {
    /* ... */
  });
  test.concurrent('concurrent test 2', async () => {
    /* ... */
  });
  test('serial test 2', async () => {
    /* ... */
  });
});
```

## test.sequential

Runs the test sequentially (the default behavior, useful to override `describe.concurrent` for a specific case).

```ts
describe.concurrent('suite', () => {
  test.sequential('runs sequentially', async () => {
    /* ... */
  });
});
```

## test.runIf

Runs the test only when `condition` is truthy.

```ts
test.runIf(process.env.RUN_EXTRA === '1')('conditionally run', () => {
  // ...
});
```

## test.skipIf

Skips the test when `condition` is truthy.

```ts
test.skipIf(process.platform === 'win32')('skip on Windows', () => {
  // ...
});
```

## test.extend

- **Type:**

```ts
// Fixtures object form (test-scoped)
test.extend<T extends Record<string, any>>(
  fixtures: Fixtures<T>,
): TestAPIs<T>;
// Named fixture form (test-scoped)
test.extend<Name extends string, Value>(
  name: Name,
  fixture: Value | ((context: TestContext, lifecycle: FixtureLifecycle) => MaybePromise<Value>),
): TestAPIs<Record<Name, Value>>;
// Named fixture form (worker-scoped)
test.extend<Name extends string, Value>(
  name: Name,
  options: WorkerFixtureOptions,
  fixture: Value | ((context: object, lifecycle: FixtureLifecycle) => MaybePromise<Value>),
): TestAPIs<object, object, Record<Name, Value>>;
// Named fixture form (file-scoped)
test.extend<Name extends string, Value>(
  name: Name,
  options: FileFixtureOptions,
  fixture: Value | ((context: object, lifecycle: FixtureLifecycle) => MaybePromise<Value>),
): TestAPIs<object, Record<Name, Value>>;
```

Creates a **new** `test` API whose context is extended with custom fixtures. The original `test` is left unchanged, and the returned API supports all `test` modifiers and further `.extend()` calls.

```ts
import { test } from '@rstest/core';

const myTest = test.extend<{ user: { name: string } }>({
  user: async ({}, use) => {
    await use({ name: 'Alice' });
  },
});

myTest('has user in context', ({ user, expect }) => {
  expect(user.name).toBe('Alice');
});
```

Fixture-aware callbacks (tests, fixtures, and per-test hooks) must declare fixture dependencies through direct object destructuring in the callback parameter (`({ db }) => ...`). Rstest does not infer dependencies from destructuring inside the function body, and object rest properties (`{ db, ...rest }`) or default values (`{ db = fallback }`) are not supported.

### Fixtures object form

Each entry in a fixtures object is a plain value, a fixture function `(context, use) => Promise<void>`, or a `[fixture, { auto?: boolean }]` tuple.

- **Plain values:** Provide non-function values directly (such as `baseURL: 'https://api.example.com'`) when no setup or teardown is needed.
- **`TestContext` access:** Fixture functions receive previously defined fixtures and [`TestContext`](#testcontext) fields (such as `{ task }`) in their first parameter `context`.
- **Setup and teardown:** `await use(value)` supplies the fixture value to the test; code before `use` is setup and code after `use` is teardown.

```ts
import { test } from '@rstest/core';

const testWithDb = test.extend<{ db: Database }>({
  db: async ({}, use) => {
    const db = await connectTestDb();
    await use(db);
    await db.close();
  },
});
```

### Named fixture form

<ApiMeta addedVersion="0.11.7" />

The named fixture form takes `(name, fixture)` and returns the fixture value directly instead of calling `use`. Because the fixture value is returned, TypeScript infers its type automatically without explicit generics. Its second parameter provides `onCleanup` to register a cleanup callback (both functions may be async):

```ts
import { test } from '@rstest/core';

const apiTest = test
  .extend('baseURL', 'https://api.example.com')
  .extend('client', async ({ baseURL }, { onCleanup }) => {
    const client = await createClient(baseURL);
    onCleanup(() => client.close());
    return client;
  });
```

Constraints for named fixtures:

- The two-argument form is test-scoped: fixture functions run per test attempt and clean up after the test and its per-test hooks finish, while plain values are reused across attempts.
- `name` must be a statically known ASCII JavaScript identifier (not `string`, template literal patterns like `` `slot${string}` ``, hyphenated names like `'base-url'`, or reserved `TestContext` fields; `Function` property names like `'name'` and `'length'` are allowed).
- Functions and classes passed directly as the second argument are treated as fixture factories. To expose a function or class itself as the value, wrap it in a factory: `.extend('predicate', () => predicate)`.

### File-scoped named fixtures

<ApiMeta addedVersion="0.11.7" />

Pass `{ scope: 'file' }` to lazily create one fixture instance shared by all tests, retries, repeats, and concurrent tests in the current file. Cleanup runs after all tests and `afterAll` hooks finish, in reverse initialization order.

```ts
import { test } from '@rstest/core';

const apiTest = test
  .extend('server', { scope: 'file' }, async (_context, { onCleanup }) => {
    const server = await startServer();
    onCleanup(() => server.close());
    return server;
  })
  .extend('client', { scope: 'file' }, ({ server }) => {
    return createClient(server.url);
  });
```

- Must be declared at the top level of the test file and cannot be overridden by a later `.extend()`.
- Can depend on earlier worker- or file-scoped fixtures; cannot access test-scoped fixtures or `TestContext` (test-scoped fixtures can depend on file-scoped ones).
- Setup is bounded by the timeout of the requesting test or hook; file cleanup is bounded by the Node or browser host.

### Worker-scoped named fixtures

<ApiMeta addedVersion="0.11.9" />

Pass `{ scope: 'worker' }` to lazily create one fixture instance shared across files running on the same worker that reuse the same extended test API/fixture definition. Cleanup runs when the worker is retired.

```ts
import { test } from '@rstest/core';

const apiTest = test.extend(
  'server',
  { scope: 'worker' },
  async (_context, { onCleanup }) => {
    const server = await startServer();
    onCleanup(() => server.close());
    return server;
  },
);
```

- Must be declared at the top level of the test file and cannot be overridden by a later `.extend()`.
- Can depend only on earlier worker-scoped fixtures; cannot access `TestContext` or file-scoped fixtures (file-scoped fixtures can depend on worker-scoped ones).
- Setup is bounded by the timeout of the first requesting test; cleanup is bounded by the worker host (a force-terminated worker cannot run user cleanup callbacks).
- In browser mode, `isolate: false` shares the fixture across files assigned to the same browser worker unless the project configures `setupFiles` (which keeps files isolated). With default isolation, lifetime equals one file.

### Fixture dependencies

Destructure other fixtures from the first parameter. Rstest initializes dependencies in topological order and tears them down in reverse order:

```ts
import { test } from '@rstest/core';

const testWithApi = test.extend<{ baseURL: string; token: string }>({
  baseURL: 'https://api.example.com',
  token: async ({ baseURL }, use) => {
    const token = await createTestToken(baseURL);
    await use(token);
    await revokeTestToken(token);
  },
});

testWithApi('fetch profile', async ({ baseURL, token, expect }) => {
  const res = await fetch(`${baseURL}/profile`, {
    headers: { Authorization: `Bearer ${token}` },
  });
  expect(res.ok).toBe(true);
});
```

### Using fixtures in hooks

<ApiMeta addedVersion="0.11.4" />

`beforeEach`, `afterEach`, and cleanup functions returned by `beforeEach` can request fixtures via direct parameter destructuring (`beforeEach(({ db }) => {})`).

- Fixtures requested by the test callback initialize before `beforeEach`; fixtures requested only by a hook initialize before that hook runs.
- Pass the fixture type explicitly to `beforeEach<Fixtures>` / `afterEach<Fixtures>` and register the hook in a suite whose tests use the extended test API (otherwise Rstest fails the test before invoking the hook).

```ts
import { beforeEach, describe, test } from '@rstest/core';

interface DbFixtures {
  db: Database;
}

describe('database tests', () => {
  const dbTest = test.extend<DbFixtures>({
    db: async ({}, use) => {
      const db = await connectTestDb();
      await use(db);
      await db.close();
    },
  });

  beforeEach<DbFixtures>(({ db }) => {
    return async ({ db }) => {
      await db.rollback();
    };
  });

  dbTest('creates a user', async () => {
    // db is initialized for beforeEach even though the test does not request it.
  });
});
```

### Automatic fixtures (`auto`)

Fixtures are lazy by default and only run when destructured by a test, hook, or dependent fixture. Use tuple syntax with `{ auto: true }` to run a fixture for every test automatically:

```ts
import { test } from '@rstest/core';

const events: string[] = [];

const myTest = test.extend({
  logger: [
    async ({ task }, use) => {
      events.push(`start:${task.name}`);
      await use(undefined);
      events.push(`end:${task.name}`);
    },
    { auto: true },
  ],
});

myTest('runs logger automatically', ({ expect }) => {
  expect(events).toContain('start:runs logger automatically');
});
```

### Type inference and explicit generics

- **Fixtures object form (`test.extend({ ... })`):** TypeScript cannot infer fixture types from an unannotated `use(value)` callback, so omitting generics causes `use`-based fixtures to be inferred as `unknown` (reporting `TS18046` under `strict`). Plain arrays and `[value, { auto: true }]` tuples can also produce wider union or tuple types without a generic. Pass an explicit generic `test.extend<MyFixtures>({ ... })` whenever you define `use`-based fixtures, tuple fixtures, or sibling fixture dependencies in an object.
- **Named fixture form (`test.extend(name, fixture)`):** Prefer the named fixture form when you want automatic type inference without writing explicit generics. TypeScript infers each fixture type from its return value and propagates it to subsequent `.extend()` calls.

The new fixture types apply only to the returned API and leave `test` unchanged:

```ts
import { test } from '@rstest/core';

// Explicit generic for the fixtures object form
interface MyFixtures {
  user: { name: string; role: 'admin' | 'guest' };
}

const objectTest = test.extend<MyFixtures>({
  user: async ({}, use) => {
    await use({ name: 'Alice', role: 'admin' });
  },
});

// Automatic inference with the named fixture form
const namedTest = test.extend('user', async () => ({
  name: 'Alice',
  role: 'admin' as const,
}));
```

## Chainable modifiers

`test` modifiers can be chained in any order before calling the test function:

- `test.only.runIf(condition)` / `test.runIf(condition).only`
- `test.skipIf(condition).concurrent` / `test.concurrent.skipIf(condition)`
- `test.runIf(condition).concurrent` / `test.concurrent.runIf(condition)`
- `test.only.concurrent` / `test.concurrent.only`
- `test.for(cases).concurrent` / `test.concurrent.for(cases)`

## Types

### TestContext

`TestContext` is passed to test callbacks, test-scoped fixtures, and per-test hooks.

```ts
export interface TestContext {
  /** Metadata of the current test */
  task: {
    /** Unique identifier, e.g. `419cefd87e_0_0`. */
    id: string;
    /** Test name provided by the user. */
    name: string;
    /** Absolute path of the current test file when provided by the runner. Added in 0.11.1. */
    filepath?: string;
    /** Absolute path of the current project's root directory when provided by the runner. Added in 0.11.1. */
    projectRoot?: string;
    /** Current retry index, starting at 0 for the initial attempt. Added in 0.11.6. */
    retryCount: number;
    /** Result of the current test, undefined if not finished yet (same shape as TestResult without fullName/relativeTestPath). */
    result?: RawTestResult;
    /** Mutable metadata copied to the current test result. Added in 0.11.1. */
    meta: TaskMeta;
  };
  /** Signal aborted with the timeout error when the current attempt times out. Added in 0.11.9. */
  readonly signal: AbortSignal;
  /** The `expect` API bound to the current test. */
  expect: Expect;
  /** Skip the current test during execution. */
  skip: () => never;
  /** The `onTestFinished` hook bound to the current test. */
  onTestFinished: (
    fn: (ctx: TestContext) => void | Promise<void>,
    timeout?: number,
  ) => void;
  /** The `onTestFailed` hook bound to the current test. */
  onTestFailed: (
    fn: (ctx: TestContext) => void | Promise<void>,
    timeout?: number,
  ) => void;
}
```

<ApiMeta addedVersion="0.11.6" />

`context.task.retryCount` starts at `0` for the initial attempt, increments on each retry, and resets to `0` for each `repeats` run.

#### signal

<ApiMeta addedVersion="0.11.9" />

`context.signal` aborts with the timeout error when the current attempt times out (including timeouts in the test callback, per-test hooks, and fixtures). Each retry and repeat receives a fresh `AbortSignal`.

Pass `signal` to APIs that support cancellation (`fetch`, `fs.readFile`, etc.) so pending operations stop when the attempt times out:

```ts
import { readFile } from 'node:fs/promises';
import { test } from '@rstest/core';

test('loads a user', { timeout: 1_000 }, async ({ signal }) => {
  await fetch('/api/user', { signal });
});

test('loads a large fixture', { timeout: 1_000 }, async ({ signal }) => {
  const contents = await readFile('./fixtures/large-data.json', {
    encoding: 'utf8',
    signal,
  });

  JSON.parse(contents);
});
```

When an attempt times out after 1000 ms, `signal.reason` is the timeout error reported by Rstest (for example, `Error: test timed out in 1000ms (no expect assertions completed)`). Node APIs like `fs.readFile` reject with an `AbortError` whose `cause` is `signal.reason`.
