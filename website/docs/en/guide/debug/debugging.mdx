# Debugging

## Debug mode

Rstest provides a debug mode to troubleshoot problems, you can add the `DEBUG=rstest` environment variable when testing to enable Rstest's debug mode.

```bash
DEBUG=rstest pnpm test
```

In debug mode, Rstest will:

- Write test temporary outputs to disk
- Write the Rstest config, Rsbuild config and Rspack config to the dist directory
- Show full error stack traces
- Set logger level to `verbose`

### Rstest config file

In debug mode, Rstest will automatically generate `dist/.rstest-temp/rsbuild/rstest.config.mjs` file, which contains the final generated Rstest config. In this file, you can know the final result of the Rstest config you passed in after being processed by the framework and Rstest.

The content of the file is as follows:

```js title="rstest.config.mjs"
export default {
  name: 'rstest',
  include: ['**/*.{test,spec}.?(c|m)[jt]s?(x)'],
  exclude: [
    '**/node_modules/**',
    '**/dist/**',
    '**/.{idea,git,cache,output,temp}/**',
    '**/dist/.rstest-temp',
  ],
  includeSource: [],
  pool: {
    type: 'forks',
  },
  isolate: true,
  globals: false,
  passWithNoTests: false,
  update: false,
  testTimeout: 5000,
  testEnvironment: 'node',
  retry: 0,
  clearMocks: false,
  resetMocks: false,
  restoreMocks: false,
  slowTestThreshold: 300,
  // other configs...
};
```

For a complete introduction to Rstest config, please see the [Configure Rstest](/guide/basic/configure-rstest) chapter.

## View test temporary outputs

In the [debug mode](#debug-mode) or when [dev.writeToDisk](/config/build/dev#devwritetodisk) is enabled, Rstest will write test temporary outputs to disk. You can view the files in `dist/.rstest-temp` directory to help you troubleshoot problems.

### Inspect bundle coverage

If a Node.js test bundle is larger than expected, enable [V8 coverage](/config/test/coverage#v8-provider) and set `DEBUG=rstest:bundle-coverage` to see which generated files the test runner received and which parts of them executed.

```bash
DEBUG=rstest:bundle-coverage pnpm rstest run --coverage --coverage.provider v8
```

Rstest prints the path to `.rstest/bundle-coverage-<timestamp>.json` under the Rstest root directory. For each test file, `assets` lists the size of each generated file in bytes, and `rawV8` contains V8 execution ranges for the generated code before source-map remapping. You can pass a test file filter to `rstest run` to focus on one bundle.

#### Common questions

- **Why is there no JSON file?** This experimental feature requires Rstest 0.11.7 or later. Check that `DEBUG` includes `rstest:bundle-coverage` and that your command runs at least one test file in Node.js. Look for `Bundle coverage file:` in the terminal for the output path.
- **Why is `rawV8` `null`?** Rstest can list assets without collecting V8 coverage. Rerun with `--coverage --coverage.provider v8` and check that the terminal shows `Coverage enabled with v8`.
- **How do I investigate a large bundle?** Start with the largest JavaScript files in `assets` and match their paths to `rawV8.entries[].filePath`. For matching entries, inspect the function ranges and execution counts, especially when many modules share one bundle. A missing entry means the coverage collected for that test has no record for that asset. Trace the imports before deciding whether to change what gets bundled. V8 offsets and asset sizes use different units, so use the ranges as a diagnostic signal.

#### Investigate with `rstest-debugging`

If your coding agent supports skills, install `rstest-debugging` and paste the prompt below with the affected test file or command. See the [installation instructions](/guide/debug/profiling).

```text
Use the rstest-debugging skill to investigate this Node.js test bundle.
Test file or command: <insert here>
Symptom: <large bundle, slow startup, or other observed problem>

Use the project's installed Rstest. Measure a representative file and the
full affected scope. If timing is part of the problem, use --trace when
available to distinguish build time from loading, setup, and test execution.

For the representative file, collect V8 coverage with
DEBUG=rstest:bundle-coverage. Correlate asset sizes with V8 execution ranges
and trace the imports behind the largest bundles. Report what the data shows
and where it is inconclusive.

If the evidence supports a change, compare one change at a time against the
baseline. Rerun both scopes without bundle debugging, with the same Node
version, test files, coverage settings, workers, and cache state. Report
whether the change improves timing while preserving test results and coverage.
Clean up only the debug artifacts you created.
```

## Debugging in VS Code

Rstest supports debugging in VS Code using `debugger` statements or breakpoints. Just open the `JavaScript Debug Terminal` and run the test command in the terminal.

You can also add a dedicated launch configuration to debug a test file in VS Code:

```json title=".vscode/launch.json"
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug Current Test File",
      "type": "node",
      "request": "launch",
      "program": "${workspaceFolder}/node_modules/@rstest/core/bin/rstest.js",
      "args": ["run", "${file}"],
      "console": "integratedTerminal",
      "internalConsoleOptions": "neverOpen",
      "skipFiles": ["<node_internals>/**"]
    }
  ]
}
```

Then you can start debugging the current test file directly in VS Code by pressing `F5` or go to the `Run and Debug` panel.
