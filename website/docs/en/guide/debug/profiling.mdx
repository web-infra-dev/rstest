# Profiling

Use `--trace`, `DEBUG=rstest`, Rsdoctor, `samply`, and Node.js built-in profilers to measure where test time and memory go.

## Using Agent Skills

Install the [rstest-debugging](https://github.com/rstackjs/agent-skills#rstest-debugging) skill when investigating performance regressions with a coding agent. It guides the agent to separate build startup from test execution before changing config or test code:

```bash
npx skills add rstackjs/agent-skills --skill rstest-debugging
```

## Common performance bottlenecks

Run [`--trace`](#using-trace) first to split build time from test execution time, then follow the matching branch:

1. **Build time dominates** (common in `jsdom` or `happy-dom`, where `node_modules` dependencies are bundled by default instead of externalized like in `node`):
   - Inspect build logs and temporary output sizes under `dist/.rstest-temp` (or [`output.distPath.root`](/config/build/output#outputdistpath)) with `DEBUG=rstest rstest run`.
   - Externalize all third-party packages with [`output.bundleDependencies: false`](/config/build/output#outputbundledependencies) (not supported in [Browser Mode](/guide/browser-testing)) or exclude heavy ones with [`output.externals`](/config/build/output#outputexternals).
   - Enable [`performance.buildCache`](/config/build/performance#performancebuildcache) for repeated `rstest run` invocations, or inspect loader/plugin compile time with [Rsdoctor](#using-rsdoctor).
2. **Test execution dominates** (fast startup, slow files or cases):
   - Check per-file and per-case durations with `--reporters=verbose` ([verbose reporter](/guide/basic/reporters#verbose-reporter)) or the `--trace` summary.
   - Profile hot runtime code with [samply](#using-samply) or [Node.js profiling](#nodejs-profiling) (see [Profiler](#profiler)).

## Using --trace \{#using-trace}

`--trace` breaks a run into per-phase, per-suite, and per-case slices. Use it when the reporter's single `Duration` number is not enough to tell where the time is spent.

```bash
npx rstest run --trace
```

The flag is opt-in. Each run records per-suite and per-case slices annotated with status and retry count, a heap counter sampled at each phase boundary, and one slice per phase of every test file:

- `prepare`: set up the worker runtime, the global API, and the coverage provider when coverage is enabled.
- `envSetup`: install the test environment. Close to zero for `node`, and when a non-isolated worker is already pinned to the environment.
- `load`: receive the built assets of the test entry. The host-side cost of producing them is reported as a host span instead.
- `setupFiles`: evaluate the configured setup files.
- `collect`: evaluate the test module and build the suite and case tree, including deferred and async `describe` callbacks.
- `tests`: run the cases and their hooks.
- `coverage`: collect coverage data from the provider. Absent when coverage is disabled, or when the file bailed or threw before this point.
- `teardown`: clean up the coverage provider and the worker state, plus the test environment when `isolate` is enabled.

Node pools also emit a `file:load` summary slice covering worker-side asset loading, setup files, test module evaluation, and suite collection (matching `TestFileResult.loadDuration`).

Browser Mode records only `prepare` and `tests`, measured on the host from the messages the page sends.

Rstest writes two files to `<rootPath>/.rstest/`, and replaces them on every watch rerun:

- `trace-<timestamp>.summary.md`: a markdown summary ranking the slowest phases, files, and test cases. The same content is printed to the terminal.
- `trace-<timestamp>.json`: a Perfetto-compatible trace for the visual UI.

Start with the summary. Open the trace when you also need to see how work overlapped across workers.

![Perfetto UI showing the trace produced by running npx rstest --trace inside the rstest repository](https://assets.rspack.rs/rstest/assets/rstest-trace-perfetto.png)

In a TTY, Rstest starts a local helper server so that the printed link opens the trace directly in the Perfetto UI. In CI, the helper server is not started. Upload the trace file as an artifact and drag it into [ui.perfetto.dev](https://ui.perfetto.dev) instead.

:::tip
To investigate a slowdown with a Coding Agent, hand it both files: the summary for the ranking, the trace for the full event data. They pair with the [rstest-debugging](#using-agent-skills) skill.
:::

## Experimental memory diagnostics

Use `DEBUG=rstest:memory` to investigate memory growth during compilation, test execution, and coverage reporting. This is an experimental debugging capability; the namespace and output format may change.

```bash
DEBUG=rstest:memory npx rstest run
```

Add `--coverage` to include coverage collection and reporting in the trace.

Rstest prints the path to `.rstest/trace-rss-<timestamp>-<pid>.jsonl` when collection starts. Save this file as a CI artifact, including for failed jobs. Each line is a JSON record written immediately, so records already written remain available if the Rstest process is killed.

The log records:

- Host RSS, V8 heap usage and capacity, external memory, and ArrayBuffer memory, in bytes, every second and at host operation boundaries.
- Compilation start and end for projects running in Node.js workers (including `node`, `jsdom`, `happy-dom`, and custom test environments), host operations with project and test-file context, and coverage collection and report generation. Final executor-map merging and cloning of the collected coverage map have separate operation boundaries.
- Worker memory at startup, every second, and before and after each test file and worker-fixture cleanup. Worker records carry `role: "worker"`, `workerId`, `pool`, PID, `threadId`, and the worker-side `sampledAt` timestamp. Active tasks also include their project and test-file path. `worker:exit` records mark the end of each worker lifetime.
- Per-project emitted asset counts and byte sizes in `project:assets` records. `jsBytes`, `sourceMapBytes`, `otherBytes`, and `totalBytes` describe the built files. `unavailableAssetCount` counts files whose sizes could not be read; totals cover the files successfully measured. Inline source maps are included in `jsBytes`.
- On Linux with readable cgroup v2 files, current memory usage, the limit, peak usage when available, and cumulative `oom` / `oom_kill` counters at startup, periodic samples, run errors, and shutdown. These files are not read at every operation boundary. `cgroupPath` identifies the sampled cgroup.

Host records carry `role: "host"`. For forks and vmForks, `rssScope: "worker-process"` identifies a separate process. For threads and vmThreads, `rssScope: "shared-process"` means the RSS already includes the host and every thread in that PID, so count it once. Heap metrics belong to each isolate and can be inspected separately. Worker ids are reused; use PID and thread id to identify a worker lifetime. Samples arrive asynchronously and may be delayed while the host is blocked. Summed RSS can count shared pages more than once. Browser processes, prebundle processes, and subprocesses spawned by tests have their own memory outside these worker records. cgroup values cover the sampled cgroup and its descendants and may include other processes or earlier activity. Periodic samples pause while the host event loop is blocked; operation-start records can still identify a synchronous operation interrupted by a kill.

`DEBUG=rstest:memory` works independently of `--trace`; combine them to also collect timing traces.

It requires the exact namespace in the comma-separated `DEBUG` value; `DEBUG=rstest` and `DEBUG=*` do not enable it. Used alone, it does not enable verbose logging or write build outputs to disk. For JavaScript API calls, the environment variable also enables collection, but the file path is not printed. In watch mode, collection continues until the session closes.

Sampling, file-write, and file-close failures are contained so diagnostic errors do not fail the tests. Memory logging adds sampling and synchronous file I/O overhead. A missing final `stop` record means collection did not close normally. Check exit status, system logs, and changes in cgroup OOM counters to determine the cause.

## Using Rsdoctor

[Rsdoctor](https://rsdoctor.rs/) is a build analysis tool that can visually display the compilation time of each loaders and plugins.

When you need to debug Rstest's build outputs or build processes, you can use Rsdoctor for troubleshooting.

### Quick start

In Rstest, you can enable [@rsdoctor/core](https://www.npmjs.com/package/@rsdoctor/core) analysis as follows:

1. Install Rsdoctor:

import { PackageManagerTabs } from '@theme';

<PackageManagerTabs command="add @rsdoctor/core -D" />

2. Add `RSDOCTOR=true` env variable before the CLI command:

```json title="package.json"
{
  "scripts": {
    "test:rsdoctor": "RSDOCTOR=true rstest run"
  }
}
```

As Windows does not support the above usage, you can also use [cross-env](https://npmjs.com/package/cross-env) to set environment variables. This ensures compatibility across different systems:

```json title="package.json"
{
  "scripts": {
    "test:rsdoctor": "cross-env RSDOCTOR=true rstest run"
  },
  "devDependencies": {
    "cross-env": "^7.0.0"
  }
}
```

After running the above commands, Rstest will automatically register the Rsdoctor plugin, and after the build is completed, it will open the build analysis page. For complete features, please refer to [Rsdoctor document](https://rsdoctor.rs/).

## Profiler

Check [`--trace`](#using-trace) first since it requires no external tooling. When you need lower-level data, pick a profiler based on what you are measuring:

- **CPU time distribution**: use [samply](#using-samply) (recommended for profiling both the main process and `forks`/`vmForks` workers together) or `--cpu-prof`.
- **Memory allocation**: use `--heap-prof` in [Node.js profiling](#nodejs-profiling) (`samply` does not collect heap data).
- **Step-through debugging**: see [Debugging test workers](/guide/debug/debugging#debugging-test-workers).

## Using samply

:::note
Profiling Node.js code on macOS requires Node.js 22.16+.
:::

[samply](https://github.com/mstange/samply) profiles the Rstest main process and test workers together.

```bash
samply record -- node --perf-prof --perf-basic-prof --interpreted-frames-native-stack ./node_modules/@rstest/core/bin/rstest.js run
```

Rstest forwards host `--perf-prof`, `--perf-basic-prof`, and `--interpreted-frames-native-stack` flags to `forks` and `vmForks` workers. For `threads` and `vmThreads`, workers share the host Node.js process, so host-level `--perf-prof*` flags already apply process-wide (do **not** pass them via `--pool.execArgv`, as Node.js `worker_threads` rejects them with `ERR_WORKER_INVALID_EXEC_ARGV`).

After the run finishes, `samply` opens the profile in the [Firefox Profiler](https://profiler.firefox.com/). Select the Node.js thread to inspect JavaScript execution time.

![rstest-samply-profiling](https://assets.rspack.rs/rstest/assets/rstest-samply-profiling.png)

## Node.js profiling

Rstest forwards `--cpu-prof*`, `--heap-prof*`, and `--diagnostic-dir` from the host `node` process to workers in all pools (`forks`, `vmForks`, `threads`, and `vmThreads`).

To collect CPU profiles:

```bash
node --cpu-prof --cpu-prof-dir=./cpu-prof ./node_modules/@rstest/core/bin/rstest.js run
```

To collect heap profiles:

```bash
node --heap-prof --heap-prof-dir=./heap-prof ./node_modules/@rstest/core/bin/rstest.js run
```

Open the generated `.cpuprofile` or `.heapprofile` files in [Visual Studio Code](https://code.visualstudio.com/docs/nodejs/profiling#_analyzing-a-profile) or [Chrome DevTools](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots).

:::tip
Host `--inspect*` flags are stripped from workers and attach only to the main Rstest process. To inspect or step through worker code, use `--pool.execArgv=--inspect-brk`; see [Debugging test workers](/guide/debug/debugging#debugging-test-workers).
:::
