# Profiling

Use `--trace`, `DEBUG=rstest`, Rsdoctor, `samply`, and Node.js built-in profilers to measure where test time and memory go.

## Using Agent Skills

Install the [rstest-debugging](https://github.com/rstackjs/agent-skills#rstest-debugging) skill when investigating performance regressions with a coding agent. It guides the agent to separate build startup from test execution before changing config or test code:

```bash
npx skills add rstackjs/agent-skills --skill rstest-debugging
```

## Common performance bottlenecks

First separate build time from test execution time:

- Slow startup and slow reruns after a small edit usually point to the build stage.
- Fast startup with slow individual files or test cases points to test execution.

Run the suite once with [`--trace`](#using-trace) to measure the split directly.

### Investigating build performance

In browser-like environments such as `jsdom` or `happy-dom`, Rstest bundles `node_modules` dependencies by default instead of externalizing them like the `node` environment. Build time often spikes when a test entry pulls in a large UI, charting, or editor package when only a small part of it is used.

**1. Check build logs and bundle size with `DEBUG=rstest`**

```bash
DEBUG=rstest rstest run
```

`DEBUG=rstest` prints verbose build logs and writes temporary build outputs to `dist/.rstest-temp` (or [`output.distPath.root`](/config/build/output#outputdistpath)). Look for long pauses in build stages or unusually large output bundles under that directory.

**2. Externalize third-party dependencies with `output.bundleDependencies`**

Set [`output.bundleDependencies`](/config/build/output#outputbundledependencies) to `false` to externalize `node_modules` dependencies in `jsdom` or `happy-dom`, matching `node` behavior:

```ts title="rstest.config.ts"
import { defineConfig } from '@rstest/core';

export default defineConfig({
  testEnvironment: 'jsdom',
  output: {
    bundleDependencies: false,
  },
});
```

Rerun with `DEBUG=rstest` to check whether build time and temporary output size drop.

:::warning
`output.bundleDependencies: false` only applies outside [Browser Mode](/guide/browser-testing), where dependencies are always bundled.
:::

**3. Externalize specific heavy packages with `output.externals`**

To keep bundling most dependencies while excluding a few heavy packages, list them in [`output.externals`](/config/build/output#outputexternals):

```ts title="rstest.config.ts"
import { defineConfig } from '@rstest/core';

export default defineConfig({
  output: {
    externals: ['react', 'lodash'],
  },
});
```

**4. Enable persistent build caching**

For repeated `rstest run` invocations across CI or local runs, enable [`performance.buildCache`](/config/build/performance#performancebuildcache) to cache Rspack compilation artifacts on disk.

**5. Analyze compile time with Rsdoctor**

If the slowdown is still unclear (for example, time spent in specific loaders, plugins, or dependency chains), inspect the build with [Rsdoctor](#using-rsdoctor).

### Investigating test execution performance

**1. Inspect file and case durations with the `verbose` reporter**

Run with the [verbose reporter](/guide/basic/reporters#verbose-reporter) (`--reporters=verbose`) to see per-file and per-case durations.

**2. Break the run down by phase, suite, and case**

Run the same tests with [`--trace`](#using-trace). The printed summary ranks the slowest phases, files, and test cases so you can tell whether time is spent in loading, setup files, or test bodies.

**3. Profile hot runtime code**

Once you know which files or cases are slow, use [samply](#using-samply) or [Node.js profiling](#nodejs-profiling) to inspect CPU time or memory allocation. See [Profiler](#profiler) to choose a tool.

## Using --trace \{#using-trace}

`--trace` breaks a run into per-phase, per-suite, and per-case slices. Use it when the reporter's single `Duration` number is not enough to tell where the time is spent.

```bash
npx rstest run --trace
```

The flag is opt-in. Each run records per-suite and per-case slices annotated with status and retry count, a heap counter sampled at each phase boundary, and one slice per phase of every test file:

- `prepare`: set up the worker runtime, the global API, and the coverage provider when coverage is enabled. It is entered twice per test file, before and after `envSetup`.
- `envSetup`: install the test environment. Close to zero for `node`, and when a non-isolated worker is already pinned to the environment.
- `load`: receive the built assets of the test entry. The host-side cost of producing them is reported as a host span instead.
- `setupFiles`: evaluate the configured setup files.
- `collect`: evaluate the test module and build the suite and case tree, including deferred and async `describe` callbacks.
- `tests`: run the cases and their hooks.
- `coverage`: collect coverage data from the provider. Absent when coverage is disabled, or when the file bailed or threw before this point.
- `teardown`: clean up the coverage provider and the worker state, plus the test environment when `isolate` is enabled.

Node pools also emit a `file:load` slice (`cat: "file"`) whose duration exactly matches `TestFileResult.loadDuration`, including when loading fails. It covers worker-side asset loading, setup files, test module evaluation, and suite collection. This overlaps the detailed loading phases and is excluded from phase and host totals to avoid double-counting. Trace slice durations use microseconds; `loadDuration` uses milliseconds.

Browser Mode records only `prepare` and `tests`, measured on the host from the messages the page sends.

Rstest writes two files to `<rootPath>/.rstest/`, and replaces them on every watch rerun:

- `trace-<timestamp>.summary.md`: a markdown summary ranking the slowest phases, files, and test cases. The same content is printed to the terminal.
- `trace-<timestamp>.json`: a Perfetto-compatible trace for the visual UI.

Start with the summary. Open the trace when you also need to see how work overlapped across workers.

![Perfetto UI showing the trace produced by running npx rstest --trace inside the rstest repository](https://assets.rspack.rs/rstest/assets/rstest-trace-perfetto.png)

In a TTY, Rstest starts a local helper server so that the printed link opens the trace directly in the Perfetto UI. In CI, the helper server is not started. Upload the trace file as an artifact and drag it into [ui.perfetto.dev](https://ui.perfetto.dev) instead.

:::tip
To investigate a slowdown with a Coding Agent, hand it both files: the summary for the ranking, the trace for the full event data. They pair with the [rstest-debugging](#using-agent-skills) skill.
:::

## Using Rsdoctor

[Rsdoctor](https://rsdoctor.rs/) is a build analysis tool that can visually display the compilation time of each loaders and plugins.

When you need to debug Rstest's build outputs or build processes, you can use Rsdoctor for troubleshooting.

### Quick start

In Rstest, you can enable [@rsdoctor/core](https://www.npmjs.com/package/@rsdoctor/core) analysis as follows:

1. Install Rsdoctor:

import { PackageManagerTabs } from '@theme';

<PackageManagerTabs command="add @rsdoctor/core -D" />

2. Add `RSDOCTOR=true` env variable before the CLI command:

```json title="package.json"
{
  "scripts": {
    "test:rsdoctor": "RSDOCTOR=true rstest run"
  }
}
```

As Windows does not support the above usage, you can also use [cross-env](https://npmjs.com/package/cross-env) to set environment variables. This ensures compatibility across different systems:

```json title="package.json"
{
  "scripts": {
    "test:rsdoctor": "cross-env RSDOCTOR=true rstest run"
  },
  "devDependencies": {
    "cross-env": "^7.0.0"
  }
}
```

After running the above commands, Rstest will automatically register the Rsdoctor plugin, and after the build is completed, it will open the build analysis page. For complete features, please refer to [Rsdoctor document](https://rsdoctor.rs/).

![rsdoctor-rstest-outputs](https://assets.rspack.rs/rstest/assets/rsdoctor-rstest-outputs.png)

## Profiler

Check [`--trace`](#using-trace) first since it requires no external tooling. When you need lower-level data, pick a profiler based on what you are measuring:

- **CPU time distribution**: use [samply](#using-samply) (recommended for profiling both the main process and `forks`/`vmForks` workers together) or `--cpu-prof`.
- **Memory allocation**: use `--heap-prof` in [Node.js profiling](#nodejs-profiling) (`samply` does not collect heap data).
- **Step-through debugging**: see [Debugging test workers](/guide/debug/debugging#debugging-test-workers).

## Using samply

:::note
Profiling Node.js code on macOS requires Node.js 22.16+.
:::

[samply](https://github.com/mstange/samply) profiles the Rstest main process and test workers together.

```bash
samply record -- node --perf-prof --perf-basic-prof --interpreted-frames-native-stack ./node_modules/@rstest/core/bin/rstest.js run
```

Rstest forwards host `--perf-prof`, `--perf-basic-prof`, and `--interpreted-frames-native-stack` flags to `forks` and `vmForks` workers, but **not** to `threads` or `vmThreads` workers. When using a thread pool, pass those flags via `--pool.execArgv`:

```bash
samply record -- node --perf-prof --perf-basic-prof --interpreted-frames-native-stack ./node_modules/@rstest/core/bin/rstest.js run --pool.execArgv=--perf-prof --pool.execArgv=--perf-basic-prof --pool.execArgv=--interpreted-frames-native-stack
```

After the run finishes, `samply` opens the profile in the [Firefox Profiler](https://profiler.firefox.com/). Select the Node.js thread to inspect JavaScript execution time.

![rstest-samply-profiling](https://assets.rspack.rs/rstest/assets/rstest-samply-profiling.png)

## Node.js profiling

Rstest forwards `--cpu-prof*`, `--heap-prof*`, and `--diagnostic-dir` from the host `node` process to workers in all pools (`forks`, `vmForks`, `threads`, and `vmThreads`).

To collect CPU profiles:

```bash
node --cpu-prof --cpu-prof-dir=./cpu-prof ./node_modules/@rstest/core/bin/rstest.js run
```

To collect heap profiles:

```bash
node --heap-prof --heap-prof-dir=./heap-prof ./node_modules/@rstest/core/bin/rstest.js run
```

Open the generated `.cpuprofile` or `.heapprofile` files in [Visual Studio Code](https://code.visualstudio.com/docs/nodejs/profiling#_analyzing-a-profile) or [Chrome DevTools](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots).

:::tip
Host `--inspect*` flags are stripped from workers and attach only to the main Rstest process. To inspect or step through worker code, use `--pool.execArgv=--inspect-brk`; see [Debugging test workers](/guide/debug/debugging#debugging-test-workers).
:::
